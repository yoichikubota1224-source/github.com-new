## 今回の登録で判明した運用上の事実 2件

### 1. `update_file` では Drive 上のファイル内容を更新できない

Drive MCP の `update_file` は**メタデータ専用**で、パラメータが `fileId` / `title` / `parentId` の3つしかなく、内容を渡す口がない。
Drive MCP の全ツール(copy / create / download / get_metadata / get_permissions / list_recent / read / search / share / trash / update)を確認したが、**既存ファイルの内容を書き換えられるツールは存在しない**。

したがって「Drive上のファイルを更新する」は、実際には次の2手順になる:

1. 新しい内容を `create_file` で登録する(**新しい fileId が発行される**)
2. 旧版を `_旧版_<元の名前>_<版の説明>.md` にリネームして退避する

今回もこの方式で、旧版(12,193B・追補a前の版)を `_旧版_00_Obsidian展開確認_20260823_追補a前版.md` に退避した。
同名ファイルの重複がないことは登録後の `search_files` で確認済み。

これは**追補方式(上書きせず追補)の規約と結果的に一致する**が、副作用として **fileId が版ごとに変わる**。ノート間リンクをfileIdで張ると版更新のたびに切れるため、**リンクはファイル名で張ること**。

### 2. 照合はファイル名ではなく fileId をキーにすること

上記1の帰結として、Drive上には**同名(または旧名を保持した)複数の版**が一時的に併存する。
今回、ファイル名をキーに照合したところ**旧版(12,193B)を拾ってしまい MISMATCH と判定された**。fileId をキーに取り直して全6点の一致を確認した。

同じ問題は8/22↔8/23でも起きている(`compi_chukyo.json` など、日付違いで同名のファイルがある)。
**照合スクリプトは常に fileId をキーにする**こと。ファイル名は一意な識別子ではない。
