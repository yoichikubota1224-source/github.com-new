## 4. ⚠ 作業中に検出した問題 5件(うち2件は当方の欠陥)

### (1) 同名ファイルで中身が違う [実]

| パス | 中身 |
|---|---|
| `predictions/20260822/results_20260822.json` | ⚠ **予想側の評価データ**(`race`/`ep_race`/`kakari`/`final`) |
| `predictions/20260823/results_20260822.json` | **8/22の確定結果**(`horses` を持つ) |
| `predictions/20260816/results_20260816.json` | ⚠ **予想側の評価データ**(`race`/`panel`/`final`) |
| `predictions/20260816/results確定_20260816.json` | **8/16の確定結果**(`horses` を持つ) |

**同じ `results_YYYYMMDD.json` という名前で、中身も置き場所も違います。**
抽出エンジンが最初に見つけた前者を読んで異常終了しました。

**対策**:
- `find_results()` は **`horses` キーの有無で確定結果を判定**し、名前では判定しません。
- **`results確定_` を優先**し、曖昧な `results_` は後順位とします。複数候補があれば警告します。
- `parse_day.py` の出力名を **`results確定_YYYYMMDD.json` に変更**し、曖昧な名前を今後増やしません。
- 今回新規取得した5日分も **`results確定_` へ改名**しました。

⚠ **既存ファイルの名前は変えていません**(原本変更を避けるため)。
命名規約の全体整理は**羊一様のご判断事項**です=[要確認]。

### (2) ⚠ 当方の欠陥 — 8/16の既存ファイルを上書きしました [実]

**事象**: 新規取得した8/16の確定結果を `predictions/20260816/results_20260816.json` へ書き出し、
そこに既にあった**8/16の予想側データ(35R・13エージェント独立再評価／commit `89584e2`)を上書き**しました。

**これは統治規則「原本変更禁止」への違反です。**

| 項目 | 内容 |
|---|---|
| 原因 | (1)の命名衝突。出力先を「その日のフォルダ＋`results_`」と決め打ちし、**既存ファイルの有無を確認せずに書いた** |
| 検出 | `git status` に `M`(変更)が1件だけ出ていたこと。新規作成なら全て `A` になるはずでした |
| 復旧 | `git checkout HEAD --` でコミット済みの原本を**完全復元**。差分0を確認済み |
| 被害 | **なし**(コミット済みだったため復元できました) |
| 再発防止 | 出力名を `results確定_` へ変更(既存の予想側ファイルと名前が衝突しない) |

⚠ **コミットされていないファイルであれば復旧できませんでした。** 運が良かっただけです。
書き込み前に既存ファイルの有無を確認する手順を、以後の取得スクリプトの前提とします。

### (3) ⚠ 当方の欠陥 — racekeyを12桁のrace_idで埋めていました [実]

**事象**: `parse_day.py` が `racekey` に **netkeibaの12桁 race_id をそのまま**入れていました。

| | 8/16 中京1R |
|---|---|
| 既存の確定結果ファイル | `07262801`(**8桁**=場07+年26+回2+日8+R01) |
| 今回の新規取得(修正前) | `202607020801`(12桁 race_id) |

**主キーは「対象日＋racekey＋馬番」**です。桁形式が違うと、**同じレースが別キーになり、
日をまたいだ結合が静かに壊れます**。抽出結果の中身は同じでも、キーが違えば別物です。

**検出経路**: 8/16の抽出結果を「新規取得版」と「既存確定版」で突合したところ、
頭数108で同数なのに**共通キーが0**でした。中身が同じなのにキーだけ全滅する — これで気づきました。

**対策**:
- `parse_day.py` に **14係の8桁racekeyへの変換**を実装。回・日が2桁になる開催では
  例外を投げて止めます(黙って壊れた値を書かない)。
- 既に書き出した5日分(8/1・8/2・8/8・8/9・8/15)の **180レース分を修正**しました。
- 全10日で **racekey桁数=8のみ / 主キー重複0** を確認済み。

⚠ **この欠陥は、8/16という「既存データのある日」を突合しなければ発見できませんでした。**
新規5日だけを取得していたら、そのまま混入していました=**突合可能な日を必ず1日混ぜる**ことを
今後の取得手順に組み込みます。

### (4) ⚠ 既存 `results確定_20260816.json` の `date` が「2026-08-23」になっています [実]

8/16のレース結果ファイルなのに、全36レースの `date` が **`2026-08-23`**(取得作業日)です。

| | 値 |
|---|---|

| 今回の新規取得 | `2026-08-16` |

**全10日を機械監査した結果、`date` が競走日と食い違うのはこの1ファイルだけ**でした。

⚠ **原本は変更していません。** 本抽出は `day` を引数から取るため結果に影響していません
(出力の `day` は全件 `20260816` で正)。ただし**この `date` を信じて結合する処理があれば
8/23のデータと混ざります**。修正の可否は羊一様のご判断事項です=**[要確認]**。
